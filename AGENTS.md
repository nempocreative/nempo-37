## Architecture rules
- Some subdirectories have their own `AGENTS.md`; read the nearest one before changing files there; why: those rules are scoped to that folder and keep this file short.
- Event saweran uses the original uploaded QRIS asset in EventSaweran, scoped to MusiComedy Night, with same-origin download and enlargement; why: preserve payment-code integrity without implying automatic payment verification.
- EventLocation renders provided map embeds with browser-safe venue destinations in event-location data; why: supplied venue links remain reproducible after remix without a new map provider.
- Event sharing uses EventShare with native device sharing and explicit web destinations as fallback; why: sharing remains usable when the browser has no system share sheet.
- Good Story Cafe reservations use the browser-safe cafe layout module for table identities, messages and their event-specific WhatsApp contact, with a locally scoped tool palette; why: event reservations must not change general service contacts or other event themes.
- After a remix, every pointer under `src/assets/` is re-uploaded into this project's storage (`lovable-assets create`) and every URL reference rewritten; a pointer carries the previous project's id, so images load in the sandbox but break once published. `src/data/media-archive.json` and the `media_archive` record keep filenames, checksums and source download URLs; why: migration must copy original files as well as code, and public Cloud Storage is blocked by workspace policy.
- Security headers are applied in Start request middleware; production sourcemaps are disabled; why: block hostile embedding and content sniffing without blocking accessibility or DevTools.
- Public news reads use explicit non-contact columns and database column grants; site settings are private; backup exports fail closed until verified server-side administrator authorization exists; why: the imported app has no real administrator authentication and client-side gates cannot protect private data.
- Main-site API requests use the root-relative `/api` prefix; event ticket reads resolve the event slug or id before querying its tickets; why: inherited parent-directory URLs can fail in previews and tickets are keyed by numeric event id.
- Graphic design prices and monthly limits live in `src/data/design-creative.ts`; WCC and LO packages live in dedicated browser-safe data modules shown on their parent Wedding/EO pages; why: each service and its rule tests share one authoritative price source.
- Current website packages, additional fees, exclusions and package-specific consultation links live in `src/data/web-development.ts`, separate from legacy digital services and business-system plans; why: website price updates must not silently change other service pages.
- MusiComedy slide variants share the frame component; the talent-free variant contains its own scoped cafe animation, respecting reduced motion; why: slide 32 atmosphere must not change slide 31's performers.
- Social-media portfolio collections live in browser-safe data with separate original image sets per tone and a shared gallery component; why: category covers, nine-post grids, and enlarged posts stay consistent without CSS recoloring.
- Invitation catalog covers use stored portrait captures of each actual closed invitation, mapped by stable theme code; why: thumbnails must match the real design and keep identical proportions across screen sizes. Refresh the capture when a cover design changes.
- Bespoke invitation designs are separate components selected by stable theme code in the invitation demo; why: refining one theme must not alter the others.
- Bespoke invitation demos use explicit leaf routes mounting NempoShell, with palettes scoped in the global stylesheet; why: each design has its own metadata and does not leak its theme into other pages.
- NEMPO 01's sample guestbook is session-only frontend state and explicitly labeled as a preview; why: example submissions must not pretend to reach a real couple or persist publicly.
- Invitation theme categories, stable sequential codes, and photo/no-photo variants live in browser-safe `src/data/invitation-themes.ts`; why: the category filters and opened invitations must use the same theme identity and photo behavior.
- Wedding concept options (tone, decor, paired bridal/groom outfits, makeup styles), the per-tone photo matrix, and consultation-message formatting live in browser-safe `src/data/wedding-concepts.ts`, rendered by the wedding concept studio; why: one source drives the compare grid and WhatsApp summary, and each tone shows complete paired outfit photos instead of CSS filters.
- Nempo Buddy lives within the shared Layout with its original mode and chat state; its chat answers and service matching live in browser-safe `src/data/buddy-chat.ts` with routing tests; why: update chat content without replacing the restored widget or changing other modes.
- Service-page prices, inclusions, and testimonial lists (all eight services: WO, invitation, sosmed, web, design, talent, business system, EO) live in browser-safe data modules under `src/data/` shared by the page and its rule tests; why: one source per price keeps pages and tests consistent. Each service page has a leaf route that mounts NempoShell and is registered in the `Switch` in `src/nempo-app.tsx`.
- The NEMPO site (migrated from Replit repo nempocreative/organizer, artifact nempo-garut-web) renders client-only through `src/components/nempo-shell.tsx`, mounted by `src/routes/index.tsx` and the catch-all `src/routes/$.tsx`; why: its 100+ pages rely on browser APIs and were ported as-is.
- Page-level routing inside the NEMPO app goes through `src/lib/wouter.tsx`, a wouter-compatible API backed by TanStack Router; why: keeps one router without rewriting every page. New pages are added to the `Switch` in `src/nempo-app.tsx`.
- tsconfig strict extras (noUncheckedIndexedAccess, exactOptionalPropertyTypes, etc.) are off; why: the imported code was written without them.
- Other Replit artifacts live in `src/apps/<key>/` (own `@/apps/<key>/` imports, `entry.tsx`, public files under `public/<base>/`) and mount at `/<base>` via `src/routes/<base>.index.tsx` + `<base>.$.tsx` using `AppShell`; why: each was a separate Vite app and they must not collide.
- Full-data JSON backup: `src/lib/backup.ts` lists every database table (a type check fails if a table is missing), `/api/backup` serves the file, and `/backup` is the download page; why: one source for "everything" so new tables can't silently drop out of backups.
- Lazily loaded pages and apps use `lazyWithRetry` from `src/lib/lazy-with-retry.ts` instead of React `lazy`; why: a page file that fails to load after an update otherwise blanks the whole screen — it retries once, then reloads once.
- Nempo Feed slide 32's downloadable video is a prebuilt MP4 (1080×1440, 30 fps, 30 s) shipped as a pointer in `src/assets/`; why: the CSS card animation must export at preview fidelity and the file exceeds the repo's 10 MB limit.
- Each homepage "Event Kami · Portofolio" card uses its own pre-composed 720×1280 poster in `src/assets/event-<slug>-poster.jpg`, fitted whole over a blurred backdrop and wired by stable event id in `src/pages/home.tsx`; why: cards must show the real poster complete with title and date legible, never a CSS-cropped or unrelated photo.
- After a remix, the migration set under `drizzle/migrations/` restarts empty and the new project's existing database tables are the baseline; why: a migration copied from the source project re-runs against tables that already exist and blocks every later schema change.
- The JSON API camelizes column names, so pages whose data types are snake_case must normalize each response with `toSnake` from `src/lib/api-keys.ts`; why: otherwise multi-word columns (guest stars, sale windows, payment info) arrive under different names and silently render nothing.
- Rows the site must always have (the MusiComedy Night event) live in browser-safe `src/data/event-seed.ts` with `eventSeedInsertSql` and are re-applied after a remix; why: a remix starts with empty tables, so the event detail shows "tidak ditemukan" unless the row is re-inserted from this one source.
- The media archive record is rebuilt from `src/data/media-archive.json` as a plain INSERT while `public.media_archive` is empty (the sandbox session has no UPDATE grant there); why: git sync carries code but no rows, so the record of every recovered file must be re-appliable from one repo file.
- One-shot database writes (re-applying seed rows) run through `psql` on the sandbox's database connection with SQL generated from the in-repo source files; why: a new file under `src/routes/` is only registered when the dev server restarts, so a temporary API endpoint never runs.
- Repository completeness is guarded by `src/lib/repo-completeness.test.ts`: every media pointer must be tracked and belong to this project's own storage, no needed file may be git-ignored, and no tracked file may reach 10 MB; why: git sync pushes tracked files only, so an ignored, untracked, oversized, or foreign-project pointer silently disappears after a clone or a remix.
- Event hero colours are derived from the event poster itself by `extractPosterPalette`/`paletteFromPixels` in `src/lib/poster-palette.ts` and applied in `src/pages/event-detail.tsx`; why: the side panel and hero wash must sit in one tone with the poster instead of a neutral black overlay that looks faded, and the palette hooks must stay above the component early returns or React hook order breaks.
